A.54.15
Write the invariant that a company program selects
Selecting a rule by its digest preserves its identity, but gives the author no syntax for changing
the rule itself. The claim example makes the missing operation concrete. Receivables are 30
and the proposed claim is 31. An author must be able to state that all claim amounts sum to
receivables, specify which state fields supply those amounts, and choose how an unknown total
affects the program. Naming an imported algorithm alone does not express those choices.
BookStateInvariantText/1 writes the existing finite invariant as explicit declarations. Global
declarations identify the book date, balances or memory leaves. Each collection identifies
a memory map or the book’s seen-event sequence. Its fields declare their types, contexts,
provenance and bindings to map keys, record fields or sequence values. Uniqueness, ordering
and reference constraints name the collections and fields they compare. Per-row blocks contain
guarded predicates and explicit row/global bindings. A final aggregate block names sums
and global inputs, then states the predicates they must satisfy. Residual prerequisites remain
attached to the row, collection, aggregate or whole invariant at which they apply.
The frontend lowers these declarations to the same BookStateInvariant/1 definition.

retained collection, total and guarded-requirement evaluators still determine every predicate’s

For the claim total, the aggregate predicate is equality between the sum of remaining claim
amounts and the receivable balance. Changing its false outcome from invalid to unsupported
changes the reason the program stops; the proposed sale still fails and its journal never enters
the accepted prefix. A more consequential edit replaces equality with “receivables are no greater
than the claim total.” That weaker predicate permits the 31-versus-30 case. The source now
controls the rule’s truth, but the altered rule has lost the original accounting reconciliation.
