# Nested assessment construction audit

26 October 2026. Dependency of accounting-term-event-carry-binding-20261026.md;
MC20/24/25/28/33/34. The inspected native step constructs six operations per
claim: insert an assessment, then replace five summary leaves. A final operation
advances the cursor. All operations are ordered by the supplied claim map.
The typed transition engine already validates complete record insertions.

The old ordered expander rejects this representation because it requires every
row field to be scalar and every operation to replace one direct scalar field.
The smallest successor keeps its expression forms and parameterized-method
constructor but checks a declared nested row definition and recursive write
templates. Scalar row reads still name direct scalar fields. Dynamic map keys
must be typed text expressions; record paths must be literal declared fields.
Both conditional branches and all operations are checked even for empty maps.
Operation identifiers use one global operation index, including the suffix.

Primary evidence is complete operation, typed-request and transition equality
against the retained assessment oracle, first on one request and then on every
retained assessment. Native lifecycle/state-request builders are disabled in
candidate construction. Full selected snapshot validation remains a separate
composition step. Unknown inputs stay unresolved; limit overflow refuses the
whole construction. A missing field, invalid insertion target, branch type
error, stale order or partial result vetoes promotion. Incorrect oracle/harness
vetoes continuation until repaired. No production/accounting admission follows.

The inherited expression evaluator is preserved in a separately named successor;
this phase changes write/schema traversal, not arithmetic or date semantics.
Source-copy provenance and exact edits are recorded by bootstrap.py. A broader
shared-module refactor would change protected predecessors and is out of scope.
This explicit maintenance cost remains a design limitation. Existing 256-write
bound is a compatibility limit, not a scientific default. Check zero rows,
nested insert type, missing/extra record fields and the operation limit before
the full finite pass. CPU only; no agents, commits, installs or external action.
