CompanyMethodAuthoring/1 writes the complete retained CompanyBookMethod/1 definition.
Its
header identifies the method and selects CompanyBookTransition/1 or /2. The remaining declara-
tions supply context and account mappings, guarded preconditions with their input bindings,
monetary calculations and effects, ordered memory changes, guarded postconditions and residual
prerequisites. The original validators still determine the meaning of each part. The text adds a
way to author their inputs; it does not introduce another accounting evaluator.
The transition version is consequential. Version 1 supports replacement of existing scalar
memory fields, such as outstanding principal. Version 2 also checks typed insertion, allowing a
credit sale to create an identified invoice claim. Its compilation environment must therefore
include the memory type definition. Both versions require an explicitly supplied book, event
and schema set. Writing a method does not reconstruct those inputs from a company name or
from its disclosures.
Each declaration occupies one line and ends with a semicolon. Precondition and postcondition
sections contain the existing requirement-exchange text, with empty event values and capa-
bilities. Their selected content digests remain checked. The monetary section declares inputs,
calculations, account roles, postings and gross flows. Expressions use references, constants,
addition, subtraction, multiplication and minimum. Types and dependencies are explicit; the
native monetary validator refuses an undeclared or forward reference, an incomplete dependency
declaration or an incompatible context. The memory section names its schemas, binds its inputs
and declares each ordered write. Binding records, types and memory templates use strict JSON
data tokens.
For example, the payment’s outstanding-principal calculation reads the existing principal and
subtracts the supplied payment amount. A memory input then names that calculation as the
value to write back. The liability posting uses the same payment amount with the book’s
signed-account convention, and the cash posting and financing flow both record its negative. A
postcondition checks that liability plus outstanding principal is zero. The text therefore exposes
the relationship between the accounting effect and the continuing contract state, rather than
merely printing a balanced journal.
The checked full payment starts with cash 100 and liability −30, pays 7/2, and finishes with
cash 193/2 and liability −53/2. A separately authored variant changes every monetary use of
the payment to one half of that amount. Its cash becomes 393/4, liability −113/4, outstanding
principal 113/4 and financing cash flow −7/4. The dimensionless multiplier retains the payment’s
context, as required by the existing product rule. This constructed variant tests whether text
changes the algorithm itself; it does not propose a rule for how much an actual borrower should
pay.
Four complete payment and claim-creating sale definitions, using two company charts, match
their typed definitions, requests and full native results. The sales increase receivables by 30,
reduce inventory by 10 and insert the identified claim with remaining amount 30; they create
no cash flow. The comparisons include balances, memory, journals and gross flow records.
Twenty syntax or environment refusal cases and twelve economic-outcome cases retain the
expected distinctions: an unknown amount is unresolved, a negative amount is invalid, and false
applicability is unsupported. A forged proposed after-state is refused by the existing application
step.

UTF-8 source slices retain their own hashes; whitespace and reordering of mapping declarations
leave the semantic identity unchanged.
