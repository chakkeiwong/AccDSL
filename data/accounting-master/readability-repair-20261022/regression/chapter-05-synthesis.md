# Chapter 5: shared meaning across replaceable components

Physical pages 80–83 turn the literature's integration problem into an
architecture. The common typed representation precedes the parser, so the
reader can understand why extraction, reviewed structured files, a Python
library and a DSL can share financial meaning. Figure 5.1 connects the stages
without making the source record disappear. The borrowing-100 example then
tests the key distinction: assuming loans of 60 and 40 must not manufacture a
new assertion that the company disclosed them.

The language comparison preserves the alternative introduced in Chapter 4.
A typed schema, SQL and ordinary Python can implement the product. The DSL's
possible value is to make recurring domain checks explicit, with maintenance,
diagnostics, migration and training costs. Building the IR and reference API
first leaves the frontend decision reversible. Shared conformance cases are
specified as a necessary comparison, not reported as proof of usability.

The reuse table is a legitimate reference comparison: each row supplies a
component, a proposed task and a checked boundary or licence observation.
Its repeated header makes the page break readable. The surrounding prose
distinguishes archived source inspection from executed integration, branch
names from version pins and project licence entries from legal conclusions
about a concrete distribution. OIM facts retain their contexts and decimals;
their calculation relationships do not reconstruct the hidden transactions.

The final ownership discussion resolves the table's central risk. Contract
tools return events, valuation tools return measures, and solvers return
bounded results. They cannot silently select accounting recognition or mutate
the ledger. Proposed language-model interpretations cannot become unsupported
facts. These concrete boundaries carry the source/history/event distinctions
from Chapters 1–4 into the architecture.
