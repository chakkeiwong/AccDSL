Construction recipes express the next step: how a permitted event supplies the values needed
by a method. MethodRecipeText/1 keeps the existing method declarations for monetary calcula-
tions, postings, cash flows, guarded conditions and memory writes, and adds explicitly typed
parameters. For example, a customer parameter can read the event’s customer input, and a
memory write can refer to that parameter. No event value is interpreted as source code. A
pointer parameter combines literal path segments and previously declared text parameters; the
existing pointer encoder escapes slashes and tildes in a claim identifier before using it as a path.
The distinction matters for the sale and collection methods. The sale writes the customer’s
name, due date, event identifier and issue date into a new claim. The collection reads the
selected claim’s remaining amount through a parameterized pointer. These values are supplied
by the actual event and current book. The accounting expressions and account choices remain
visible in the recipe. An author need not reproduce a serialized method tree or maintain its
selection hash manually. Missing, unused, forward or mistyped parameters are refused by the
original contextual constructor.
An assessment requires a sequence of writes over the current claims. OrderedExpansionText/1
contains the complete base recipe, map path, row types, per-row replacements and final
replacements. Each replacement declares its identifier, path and value expression. A row
expression can read a field, the current key, an event input or event date, and choose between
typed branches of a date condition. Both branches are checked even when only one will be
evaluated. The explicit assessment-key order determines the write sequence; a duplicate or
incomplete order refuses construction. A malformed row expression also refuses when the map
happens to be empty.
Four scalar recipe sources and two ordered-expansion sources reconstruct their complete tem-
plates. Across 18 scalar and 20 expansion cases, the full construction results, transition requests
and transitions equal the retained typed comparisons. These checks include identifiers containing
slashes, tildes and Unicode. Source lowering reports syntax and structure only; the current
book, event, schemas and memory definition remain necessary for contextual construction. Thus
a reusable recipe is not prematurely described as a method valid for every possible state.
SelectedCompanyText/1 joins these declarations. It imports the opening book, schemas, statement
mapping and memory definition by exact content identity. Those four resources contain facts
and types. The opening rule, invariant, eligibility and construction algorithms are inline source
blocks. Roles, unit-cost pointer and policy define the selected company conventions. Events
retain their full typed inputs, provenance and declaration order; reports and carry commands
retain their dates, notes, equity movements and explicit memory policies. The native-shaped
admission input is derived from these same facts and projected commands, rather than authored
as an unrelated second copy.
