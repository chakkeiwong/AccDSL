14.9
Decisions and replaceable assumptions
The requirements fixed by this design are preservation of evidence and alternatives, explicit
time and basis, balanced and admissible posting, economic state beyond journals, and distinct
set/probability semantics. Replaceable choices include the storage engines, parser generator,
solver, numerical libraries, aggregation resolution and user interface. Every scientifically material
aggregation, behavioural parameter, prior or truncation rule must record provenance, purpose,
failure mode and a diagnostic before it becomes a default.
The immediate work is to finish and review the governing proposal, including its real-source,
authority, domain and research obligations. Product implementation follows completion of that
work and explicit implementation authorization. In the table above, P0 establishes portable
records, review/time selection, durable receipts and typed authoring; P1 builds admitted
histories; P2 connects the corporate methods and matched textual frontend. These stages are a
design sequence, not an already running product campaign.
14.10
Concrete conformance and corpus protocol
The fixture directory contains independently entered inputs and expected outputs for Northstar,
rounded borrowing, evidence views and sector cases.
check_repair_conformance.py recom-
putes exact journals and statements, constructs the joint linear bridges in Z3, checks strict
bounds, and exercises replay, atomic rejection, finite Bayes updating and funding failure.
check_core_contract.py checks grammar/schema examples, canonical identities, stable streams,
information restrictions and source inventory. These scripts are reference oracles for portions of
the design. They do not test an unimplemented full DSL compiler, all adapters or standards
compliance.
Every conformance case must specify input files, the operation requested, expected values or
typed errors, comparison convention and supported scope. Exact money, finite probabilities,
linear witnesses and example journals compare as rationals. Approximate valuations require an
error bound or a justified tolerance tied to the valuation scale. A missing expected result cannot
become a passing test simply because the operation returned something. An implementation
release must pass all applicable positive and negative fixtures and preserve unresolved operations;
the arithmetic oracle alone does not release it.
