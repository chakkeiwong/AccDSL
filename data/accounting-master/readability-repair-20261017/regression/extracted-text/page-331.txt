Implementation contracts
13.1
Reference implementation and component boundaries
The proposed reference implementation uses Python for orchestration and a deterministic refer-
ence evaluator, exact decimal/rational arithmetic for booked amounts, SQLite for transactional
metadata and versioned records, and columnar files for large scenario outputs. DuckDB is an
optional analytical reader. These are convenience choices justified by inspectability and modest
initial scale; they do not establish production performance. The IR and conformance tests
allow a later compiled executor without changing accounting meaning. Committed journals,
economic deltas, receipts and branch heads belong to the one transactional store, including
for simulation branches. Columnar files hold derived analytical exports, never independently
writable committed books.

The first service boundary is local and synchronous. A job abstraction can be added for
extraction and simulation without requiring distributed execution. The model compiler returns
an immutable execution plan; the executor receives that plan and run inputs. Neither should
retrieve live market data implicitly. Input datasets and rule packages are selected and versioned
before execution.
13.2
Persistent records
The table identifies logical storage relations and their obligations; exact versioned record schemas
determine their payloads. Candidate calculations and diagnostics remain separate from the
committed accounting relations.
