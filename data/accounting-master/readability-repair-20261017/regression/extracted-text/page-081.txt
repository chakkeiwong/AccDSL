Why a DSL, and when another approach is better
The strongest baseline is a typed schema, SQL storage and ordinary Python code. That
combination can implement the whole product. Its disadvantage is that repeated accounting
requirements can become conventions scattered across functions: implicit currency conversion,
missing period checks, hidden default values and duplicated rule selection. A bounded language
makes these requirements part of typing and compilation. Its costs are language maintenance,
diagnostics, migration and training.

The decision is to implement the IR, validators and Python reference API first, then the textual
frontend. The same conformance cases must pass through both frontends. If the DSL fails to
reduce ambiguity in representative authoring tasks, the IR and library remain useful. This is a
reversible product decision, not a claim that a new language is inherently better than a library.
