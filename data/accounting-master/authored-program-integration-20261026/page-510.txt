A.55.2
A sale needs an earlier live lot
Snapshot membership cannot show that a lot existed before a sale. The retained comparison
makes this concrete by giving settlement and sale the same date and placing the sale first.
Date ordering then passes, but the native method rejects the sale because the lot does not
yet exist. A second sale and a second complete settlement expose similar limitations. These
failures motivate an explicitly ordered identity check rather than a stronger interpretation of
the snapshot.
MethodIdentityLifecycle/1 declares named identity pools, their initial live and retired members,
and a closed action mapping. Each action contains an ordered list of create, require or consume
operations. Create requires an identity absent from both live and retired memory. Require
checks that an identity is live without changing it. Consume moves a live identity into retired
memory. Retaining retired identities prevents an already used identifier from being silently
created again.
For the conditional return example, settlement consumes the live return-component identity
and creates a recovered-lot identity. Sale consumes that lot. Consuming the component makes
a second complete settlement fail; consuming the lot makes a second whole-lot sale fail. The
supplied order also makes a sale before creation fail, including when both events have the same
date. The initial empty retired pools in this example are explicit assumptions of its synthetic
opening. They are not evidence about an actual company’s lifetime event history.
Each event’s operations run against a private copy of the identity pools. Only when every
operation succeeds does the diagnostic trace adopt that event’s result. If a later operation fails
or needs an unknown key, no partial identity change from that event survives. Earlier successful
steps remain visible with their indices and after-states. This is local identity atomicity: no
money is posted, no journal is authorized and no durable transaction is committed.
Unknown initial identities or incomplete initial pools stop the trace before its first event. An
incomplete event sequence also stops before any observed event, because an omitted predecessor
might create or consume a needed resource. With a complete sequence, an unknown action or
operation key stops at that event. Later state is not inferred. All observed rows still undergo
structural checks, and independent snapshot findings remain available. An otherwise complete
identity trace can therefore coexist with an unresolved snapshot condition; the combined result
does not report success.
The four retained failures—sale before creation on an equal date, a missing sale lot, repeated
whole-lot sale and repeated complete settlement—are all rejected by this explicit identity
sequence.
