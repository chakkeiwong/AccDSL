# Close the AccDSL release gaps

27 October 2026. Based on the [release-readiness audit](../../data/accounting-master/release-readiness-audit-20261027/result.md),
cutoff Version 5.50. Covers MC01–35, G1–G18, all six interactions, 46 operations,
nine literature gaps and 18 closure packages. This plan specifies the route to a
scholarly/specification release; it does not authorize publication, paid review,
production implementation or empirical forecasting experiments. Preserve the full
mission, frozen evidence and independently active work.

## Objective and evidence contract

Question: can the identified release candidate explain, specify and substantiate
its supported source-to-history-to-scenario behavior sufficiently for a reader
and an independent implementer, with reproducible evidence and explicit limits?

Baseline: exact source/PDF identities in the audit's baseline.json, current
mission acceptance wording, and each package's existing evidence. Before execution
refresh the live delta; if it changed, reconcile the changes rather than replaying
this plan against a stale version.

Primary completion criterion: all design-release acceptance conditions have an
explicit supported disposition, all promoted claims have adequate evidence, and
independent review findings have been resolved on a reproducible identified
candidate. Counts, pages, elapsed time, syntax checks and balanced statements
are explanatory only. A local source gap vetoes its dependent claim, not unrelated
work. A missing normative dependency, changed target, lost feasible history,
unsupported accounting admission, corrupt source identity or invalid oracle
vetoes the affected result and triggers repair. Do not claim universal completeness,
current accounting compliance, scalability, empirical advantage or forecasting
accuracy from these checks.

Preserve the result in one release acceptance matrix, claim/source index,
conformance index, dependency manifest and review record. Link detailed evidence
instead of copying every historical record into new appendices.

## Dependency sequence and exact deliverables

### C0 — Establish the release boundary and reconcile the master (R01)

Dependencies: live baseline refresh only. MC01–35, MC33/34 especially; all W.

Produce release-acceptance.json/md with one row per original condition and a
claim/profile inventory. Each row contains original wording, release class,
supported subconditions, exact current evidence, unresolved subcondition, owner,
next action and a reasoned disposition. Separately label historical versus current
next actions; preserve frozen records. Reconcile completed conversion, policy,
coupon and credit work before choosing new tasks. Use the existing
accounting-master-acceptance-priority-20261027.md as the operational starting point.

Exit: every broad row has a meaningful current decision or a precise missing
subcondition; no generic “still open” stands in for analysis. Every active next
plan points to unfinished work. A proposed unsupported disposition must cite the
original acceptance provision allowing it. If none exists, the method remains a
release blocker or requires an explicit user scope decision; do not invent a waiver.

### C1 — Recover and lock the reproducible bundle (R03)

Depends on C0's included claims/profile list; inventory can begin immediately.
MC24/25/30/31/32/33; W11/12/14/17.

Resolve core-ir.schema.json and core-contract.md references to exact existing
versions. Supply documented roots/build instructions and a transitive dependency
map for all claimed examples. Separate public release files from locally retained
restricted papers/standards; include reproducible retrieval/access dispositions
where redistribution is unavailable. Lock environment and selected dependency
versions with notices and hashes. Add a verifier that reads frozen evidence and
writes only to a new staging/output directory. Do not rerun accepted one-shot
writers to create a passing package.

Exit: no unresolved normative reference; no hidden dependency on a developer's
home directory; a declared recipient can identify every required file and command.
A truly unavailable required dependency blocks the associated reproducibility
claim. Optional dependency omission must have an explicit supported boundary.

### C2 — Consolidate one implementable specification (R02/R04/R08)

Depends on C0, uses C1's version map. MC02–18/23–28/32; W02–06/11–13/17.

Write a normative compatibility map covering source/evidence, clocks and actors,
uncertainty kinds, family representation, model/policy domains, monetary and
memory effects, accounting book, report and result status. Name authoritative
profile versions and mappings; do not force incompatible historical profiles
into one signature. Specify types, formulas, errors, refusal behavior,
complete/partial results, root/rounding conventions and migrations. Connect
proofs/derivations to exact assumptions and executable golden cases.

Resolve the complementary alpha convention and stale-present-tense profile
statements in a protected successor. Preserve teaching progression while making
later supported scope findable. Treat general mixed/continuous compression,
inference and financing results as separate claims with explicit premises; no
finite example silently establishes the general result.

Exit: a fresh implementer can derive each supported input, transition and output
without guessing from private scripts. All conflicting meanings have a recorded
resolution. Full durable storage implementation is not required for design
acceptance, but its required semantics and later validation are specified.

### C3 — Close consequential source, accounting and literature questions (R05/R07)

Depends on C0's consequential claim list. Can proceed alongside C1/C2.
MC13–22/29–31/35; W05–10/14/15.

Prioritize conversion-to-control allocation, positive recovery admission and the
actual insurance shared-group interaction against their current independent
plans. Begin by reading the latest results, since these tasks may advance while
the release is consolidated. For each promoted treatment supply facts, timing,
applicability/edition, source anchors, proposed answer, competing interpretation
and complete accounting consequences. Preserve unresolved alternatives where
support does not discriminate them.

Build one current claim-to-source index across the old six ledgers and later
supplements. Read consequential technical methods/theory/appendices and official
code; close version mismatches; disposition direct competitors and unavailable
sources. Do not reacquire known failures without a new legitimate lead. Do not
call available-but-unread literature blocked.

Exit: every release claim is supported, correctly limited, or removed from the
promoted claim set under a scope decision permitted by C0. Required methods
cannot disappear simply because a source is hard to obtain. A missing source
blocks dependent promotion, while other ready work continues.

### C4 — Complete the integrated evidence spine (R06 plus R04/R05/R08)

Depends on the relevant C2 and C3 interfaces/authority; case preparation can start
in parallel. MC01–22/24–28/33/34; W01–13/16.

Connect one full known-history synthetic case and the required named annual/
interim disclosure package to observations, admissible alternatives, actor
information, scenarios, financing, journals and all affected statements. Keep
unknown real history explicit. Add the sector/group interactions required to
establish the shared core, with exact original/revised/failed-prefix outcomes.
Enter independent expected full states and reports before running new cases.

Map the 67 original, 48 literature and 86 cross-interface failure rows to a
case, derivation, justified out-of-profile refusal or a precise remaining task.
Check combinations by shared state/assumption dependencies and important pairwise
or higher-order joins; do not generate an enormous Cartesian test list. Add any
new failure discovered. Label observed evidence separately from proposed tests.
For approximate methods specify the target and uncertainty/error criterion before
execution; exact examples do not validate stochastic accuracy.

Exit: all critical selected facts/operations have an independently reviewed
answer or a correctly specified unresolved response; complete outputs and failure
statuses match. A missing feasible branch, hidden funding, future-information
leak, unsupported treatment or silent renormalization vetoes the affected claim.
This is not an eight-year forecast study or a claim of exhaustive failure coverage.

### C5 — Perform the full manuscript and source regression (R02/R07)

Depends on a stable C2–C4 candidate. MC29/30/32–35; W15/17.

Read the whole main argument and normative reference sequentially in manageable
units, with a current section/equation/claim map. Distinguish identity, assumption,
equilibrium condition, imported result and local deduction. Check exposition and
premises where equations are used. Verify citations against the actual technical
anchors, not only bibliography keys. Record each confirmed defect and repair it
in the manuscript. Retain reasons for contextually sound passages.

Build both volumes from the protected successor, inspect the actual rendered
pages and connected references, compare source/math/citations with the protected
baseline, and investigate every substantive removal. Preserve an appendix as a
lookup reference where that is its purpose; do not add administrative scaffolding
to the scholarly narrative. No fixed percentage or style score establishes reader
comprehension.

Exit: all internally identified material inconsistencies are resolved, both
volumes have honest whole-document coverage, and remaining review questions are
specific. Human voice and comprehension remain subject to independent feedback.

### C6 — Reproduce in an isolated staged bundle (R03/R04/R06)

Depends on C1–C5. MC24–26/30–34; W11–14/16/17.

Use documented environment/build commands and an output directory distinct from
frozen evidence. Verify transitive paths, immutable inputs, expected semantic
results, positive/negative fixtures and both volumes. Record actual command,
environment, code/source identity, intentional CPU mode if relevant, duration,
outputs and failures. Byte-identical PDFs require controlled timestamps/toolchain;
otherwise define semantic equivalence separately from content identity and explain
any expected nondeterministic metadata. Do not relax financial result comparisons.

Exit: an independent clean copy reproduces all declared evidence with no hidden
files, silent downloads, source mutation or undisclosed exclusions. If the oracle
is circular or the environment cannot implement the stated target, repair the
harness before drawing a scientific conclusion.

### C7 — Obtain separate acceptance and assemble the release decision (R09)

Depends on internal C0–C6 completion. MC32–35; W17/18.

Prepare distinct reader, implementation and domain review packets bound to the
same candidate. Include the proposed answers, sources, adverse cases and precise
remaining questions. Record who reviewed what and what was not reviewed; repair
findings and rerun affected checks. A changed candidate needs a scoped regression.
Request user authorization only for external engagement/publication not already
authorized; this plan performs neither. Internal drafting continues while human
feedback is unavailable, but acceptance remains pending.

Exit: all relevant design acceptance decisions and review findings are resolved
on one identified candidate; known limitations and later product/forecast duties
are visible. Only then prepare a release manifest and a concrete publication
proposal for the user. Do not promote S6/E3 from document checks.

## Product and empirical work retained outside this release decision

A software release additionally needs the implemented common runtime, real-store
transactions, concurrency/crash recovery, packaged compatible dependencies,
matched adapter execution, measured workload/resource behavior and operational
security/data handling appropriate to deployment. A forecasting release further
needs genuine historical availability, declared targets and admissible models,
heldout/adjudicated data, fair tuned comparators and downstream uncertainty-aware
evaluation. These are retained duties, not evidence already supplied by the PDF.

## Skeptical review before execution

The first draft of this route could have demanded that all 18 broad packages
close before any design release, or treated unsupported labels as permission to
waive them. Both would be wrong. C0 now preserves original acceptance conditions
and separates subcondition/release class explicitly. The opposite risk is to
call an optional source or runtime absent without checking later evidence. Every
phase therefore begins with current successor reconciliation.

The plan passes the local skeptical audit because it uses a hash-bound baseline,
separates evidence classes, avoids count-based promotion, checks hidden defaults,
requires independent expectations and provides local failure/repair decisions.
No command is justified merely because it produces another artifact. The actual
commands and evidence contracts for new numerical experiments must be reviewed
in their unit plans before execution. Isolated build/conformance checks do not
establish empirical merit. Pending human review blocks final acceptance, not
internal preparation. No calendar estimate is asserted without a closed work list.

Stop conditions: invalid or drifting baseline requires re-snapshot/reconciliation;
missing required authority blocks its treatment; a corrupt/circular oracle blocks
its result; failure of a candidate method triggers the planned repair rather than
abandoning the whole direction. Independent ready work continues. The audit task
ends after the gap map/plan/readback; it does not execute C0–C7 automatically.
