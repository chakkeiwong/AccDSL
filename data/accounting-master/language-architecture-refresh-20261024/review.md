# The next language gap is reusable method requirements

24 October 2026. Version 3.58 is a 426-page provisional design, not_ready.
The source work now describes the retained Apple statements and their unresolved
execution inputs precisely. It does not supply a general compiler, method
registry or reusable state-admission procedure. Adding another fixed-source
wrapper would not resolve that distinction.

## Inspected boundaries

| Contract | What is reusable | What remains case-specific or missing |
|---|---|---|
| CompanyOperationsDraft/1 | Closed operation records, identified claims, arithmetic and shared annual book | Fixed chart, full calendar year, restricted inventory/tax/financing methods; prerequisites embedded in Python checks |
| ReturnModuleAuthoringDraft/1 | Closed component/lot/tax declarations; known-invalid/unsupported/unknown distinctions | One complete-return/whole-lot route; profile findings and scalar control equations encoded directly |
| RetainedCompanyProgramDraft/1 | Explicit capability identities and ordered event selection; caller findings separate | Source, opening and 13 events bind synthetic P; capabilities are implementation identities, not general prerequisite declarations |
| SourceConstrainedCompanyStateDraft/1 | Explicit fiscal intervals, source identity and conditional measurement interpretation | Apple finite binder, no account allocation or executable latent state |
| RetainedStatementContextDraft/1 | Matched observation/relation authoring; explicit stock/flow context roles | Retained ledgers and named role definitions; no general concept mapping or actual-history solver |
| CompanyComposition/1 | Legal books, shared lot memory, tax origins, explicit atomic/retry semantics | Supplied P/S facts, restricted migration and methods; not arbitrary module composition |
| SectorCompany/1 | Explicit legal/sector state, tax/FX/ownership and supported component mappings | Fixed bank/insurer examples and findings; valuations, prudential state and general imports remain separate |
| Portable MethodDefinition / ExtensionPackage | Existing declared state schemas, preconditions, contexts, authority and capabilities | A common typed predicate representation/evaluator and machine-checkable bridge to current profiles are not demonstrated by these increments |

The last row is already specified conceptually in the portable reference and
interfaces-contract-v1.md. The next task must instantiate that existing design,
not claim to invent method preconditions. A capability hash proves which code
was selected; it does not explain which state, evidence or scope permits use.

The current state meanings must remain distinct: a reported consolidated amount,
a conditional measurement interval, a legal trial balance, a contract/cohort
state, a source-admission finding and a numerical estimate are not substitutes.
No generic truth evaluator may turn a caller Boolean into an authoritative
accounting decision. Structural validity, domain applicability, unresolved
evidence and successful execution require separate outcomes.

Default audit: JSON Schema validates structure only; exact rationals are a
calculation convention, not exact source truth; three-valued findings require
dependency-aware propagation; a manifest registry is caller-owned and immutable
by request. The next plan must test a changed known scalar, unknown scalar,
false review and unavailable method independently before promoting any result.

The strongest alternative is that existing portable machinery already supplies
an interoperable predicate evaluator. The inspected contracts describe required
fields and consequences, while current profiles implement those checks separately.
Finding a compatible existing evaluator would trigger reuse instead of new code.
No missing real fact, pending human review or failed candidate has fired a global
continuation veto. Internal design work remains ready.
