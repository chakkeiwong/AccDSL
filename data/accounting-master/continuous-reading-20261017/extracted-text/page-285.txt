Retry the event without repeating its accounting
The business-event lookup key remains the entity, book, branch and business-event identifier.
After input validation, an equal request fingerprint returns the original receipt before testing
the freshness of today’s head. Suppose all four events have committed, advancing the head from
generation zero to generation four. Retrying the original finance request returns its original
receipt and closing state at generation one. The response separately reports the observed
generation-four head and that this invocation made no additional commit. It does not apply
finance again or replace today’s state with the old closing state.
Equality covers the complete request, including its request identifier, budget, original expected
head and dependency identities. Changing any of those bytes while retaining the business-event
key is a conflict, not an exact retry. A previously unseen event with an old head is stale. The
transaction repeats both the key and head checks before publication: an identical request that
has just won returns its receipt; different request bytes for that event conflict; a different event
that advances the head makes this request stale. In each case the competing transaction’s
changes are distinguished from any changes made by the requester.
If the acknowledgement disappears, the client cannot infer whether the transaction committed.
The exchange therefore records a transport observation with unknown commit status, the
original submission and its exact request bytes. It does not invent a received operation result.
One possible storage state still has the opening head and no receipt; the other has the complete
closing state and receipt. Resubmitting the exact request commits once in the first case and
returns the old receipt in the second. A timeout supplies no reason to change the event identifier,
opening head or economic facts.
These finite examples check the equations, complete record bindings and required decisions
for both storage states. They specify observable behavior; actual transaction isolation, crash
recovery and durability need later implementation tests. Their completed coverage is a decision
on one request, with no interpretation as probability mass over financial histories. The underlying
source applicability and supplied actuarial assumptions of the connected-group example continue
to govern its accounting meaning.
12.8
PAA, reinsurance and valuation methods
The preceding premium-allocation case states separate eligibility and recognition timing for gross
insurance and reinsurance. PAA under 53–59 requires the one-year coverage or nonmaterial-
difference condition; a short payment lag is not the eligibility test. LRC starts with received
premium and applicable acquisition adjustments, then releases insurance revenue under the
prescribed service pattern. LIC still measures incurred obligations using the applicable fulfilment-
cash-flow rules; the allowed short-settlement discount simplification needs its own conditions.
Emerging onerous facts require a loss assessment; a premium balance cannot be presumed
sufficient.
