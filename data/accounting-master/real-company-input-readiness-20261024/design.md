# Retained disclosure input readiness

This reference answers whether the retained Apple package can supply either
CompanyOperationsDraft/1 or RetainedCompanyProgramDraft/1. It reads named
retained sources. It neither reconstructs Apple nor admits an as-of history.
The governing plan is docs/plans/accounting-real-company-input-readiness-20261024.md.

## Audited boundary

The implementation will bind the exact packet bytes, issuer, package, named
view and target profile. All 139 inventory entries and all four original
statement collections remain identifiable. Selection of observations depends
on the view's source identities; neither later comparative readings nor another
issuer's records can be substituted. Inventory and unresolved obligations are
retained as package-wide documentary context, not additional admitted facts.

Each input requirement records target fields, selected observations, original
obligation references, the limitation, affected operations/reports/carry, and
the next evidence or design needed. Displayed amounts retain their original
literal, context, precision, reading pointer and admission status. A reported
dash remains a dash. The separately labelled arithmetic of displayed current
and noncurrent term-debt captions is not an instrument schedule or total debt.

Explicit caller assumptions have their own identities and provenance. In this
readiness-only profile they are documentary proposals, never executable input
values or source facts. They do not resolve a required input by their presence.
No missing input is replaced by zero or borrowed from a synthetic company.

The request has a closed JSON schema. The result is a deterministic projection
whose acceptance contract is exact recursive equality to fresh evaluation of
the bound request and packet. That rejects extra keys and modified dependency,
context, amount, assumption or decision fields at any depth; serialization
alone is not a result validator. This finite checker accepts no third target,
new packet or later-only view. Those require a separately reviewed extension.

Results preserve two independent sets: unavailable required state and unsupported
target scope. The known target mismatch remains visible even if other inputs
are unknown. The only valid execution decision for these retained source/target
combinations is blocked, with no opening, journals, complete report or carry.
This is a finding about the selected finite target, not a proof that Apple
cannot be represented or simulated by a broader design.

## Research intent and acceptance

Question: which source amounts remain useful, and which precise dependencies
prevent execution? Comparator: retained record bodies, 139 inventory items,
102 annual, 100 interim, 27 annual-opening and 27 interim-comparison readings,
plus the actual target validators. Expected failure: aggregation and fixed
target assumptions leave indispensable state or scope unresolved.

Pass requires exact preservation, complete target-field coverage, independently
checked selected amounts/counts, rejection of forged identities/results and
explicit execution refusal. Counts are explanatory only. Corrupt indispensable
input is a continuation veto for that dependency; missing state and unsupported
scope trigger further design. Neither acceptance counts nor a blocked result
promotes accounting correctness, full semantic closure or infeasibility.

Defaults audited: exact rationals preserve displayed tokens only; original
inventory is retained without reclassifying completion; target validators are
diagnostic baselines, not immutable product requirements; named-source views
need no invented historical timestamps. Early checks test each of those limits.
The next repair should expose fiscal periods and partial source-constrained
state without fabricating a legal opening or choosing an arbitrary latent
history. A separate reviewed plan must govern that repair.

## Preservation and execution

Use local retained sources only and CPU-only deterministic checks. Protect
packet, source inputs/blobs, target validators and predecessor evidence with
hashes. Record once after checks; read-only replay recomputes every output and
checks recorded hashes. Existing reference packages and Version 3.56 stay
unchanged. MC01–07/10/11/15/16/18/24/27/28 advance only within this boundary.
