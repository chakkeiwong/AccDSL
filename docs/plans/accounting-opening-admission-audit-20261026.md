# Audit the remaining native opening-admission dependency

26 October 2026. MC15/20/24/25/33/34; S2/S3/S4. The explicit program
composer now covers execution, including reports/carry and stopped prefixes.
The next question is narrower: what exactly remains in native opening
admission, and can it be represented without inventing a weaker baseline?

Inspect native validate, prepare_opening, event_types, claim_type, control,
operating.build and opening report checks. Map each obligation to its existing
typed/state/report owner or a genuinely new declared condition. Preserve type
shape, capacities, roles, unit-cost pointer, empty-map convention, opening
cursor, policy provenance, report mapping and complete command validation.
Do not treat a valid typed book or zero claims as equivalent to all those checks.

Audit baseline: the two original native opening/program bodies. Use targeted
mutations to expose rejection order and controls which are not actually checked
until execution. Return full native refusal or success plus exact edited input;
record caller/program versus opening-specific scope. Existing functions may be
used as comparators, never silently relabeled a new declarative implementation.

Primary criterion is a complete source-anchored obligation map and discriminating
counterexamples sufficient to write a successor design. Counts are explanatory;
this audit makes no new conformance/completeness claim. Missing or ambiguous
ownership is a repair trigger. A contradiction in the baseline must be stated,
not patched in frozen code. No new financial assumption, accounting admission,
agents, commits, installs, GPU, fees, outreach, publication or E3.
