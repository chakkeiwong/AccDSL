# Bind method requirements to explicit input records

24 October 2026. S2–S4; MC02/04/05/10/13/15/17/24/26/27/31 and G2/G3/G10/G13/G15/G17.
Preserve Version 3.59 and the recorded MethodRequirements/1 core/frontend.

The requirement interpreter is reusable, but current legacy bridges construct
its input declarations and values with case-specific Python. The next question
is whether a caller-owned, declarative input map can bind a requirement manifest
to exact typed record contents while retaining identities, unknowns, roles and
contexts. This must not become implicit source-to-ledger allocation or a claim
that reported data is an executable opening.

Skeptical audit: a path alone identifies neither bytes nor meaning. A hash alone
does not prove source authority. Source-role/context mismatches must not be
hidden by a mapping, and unknown conventions differ across legacy records.
Do not make the mapping invent units, zero values, scalar types or financial
findings. Independent source record identity, manifest identity, context
declarations and explicit decoding rules are required before scalar assessment.
The existing imperative bridge is a comparator, not automatic promotion.

Before implementation inspect current JSON-pointer and content-registry helpers
for reuse. Specify exact pointer escaping, array indices, absent paths, duplicate
bindings, unsupported nested/scalar conversions and size/depth limits. Preserve
unknown annotations separately from structural errors. Unknown legacy sentinels
may be interpreted only under an explicit declared encoding, never universally.

Primary criterion: record-bound values and assessment match independent expected
records and the selected existing bridge under exact context/role declarations.
Changed record or manifest bytes, swapped contexts, duplicate mapping, invalid
pointer or hidden coercion veto acceptance. A missing fact may yield unresolved;
a corrupt binding is invalid. Identity and missing-input tests are correctness
criteria; counts are explanatory. No source/accounting admission, full method
eligibility, real-company reconstruction, production or forecast result follows.

Sequence: inspect reusable pointer helpers; write the binding specification and
default audit; implement a small generic binder with caller-pinned record/schema
and explicit missing-value conventions; test two method records plus independent
reported/legal context counterexamples; record/replay; refresh the master and
audit the next discriminating full-method composition work.

Retain the distinction between source evidence, caller assumptions, legal book
state and review findings. A record digest identifies supplied bytes, and a
binding declaration identifies the caller's interpretation; neither is an
accounting approval. Any transport provenance must describe mutations honestly
rather than citing an unchanged fixture as the exact source of altered values.

CPU-only deterministic checks. Artifacts:
data/accounting-master/method-input-binding-20261024/. No numerical experiment,
external action, professional review, production release or forecasting.
