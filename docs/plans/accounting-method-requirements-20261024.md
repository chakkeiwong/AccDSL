## Question and skeptical audit

Can the preconditions already required by MethodDefinition be expressed once
as typed, reusable declarations and assessed consistently across current
company methods? The comparator is the inspected profile code, together with
independently specified truth tables and arithmetic examples. A new fixed-case
wrapper or a renamed collection of Python callbacks would not answer this.

The architecture review found schemas and method-definition records but no
compatible common predicate interpreter in the inspected current paths. Search
the remaining predicate/truth implementations before adding one; reuse a
compatible evaluator if found. Record the search scope, including limitations.
Do not claim code absence for the entire repository from a bounded search.

Material risks are conflating known contradiction with unknown evidence,
promoting a caller finding to authority, overlooking context or unit mismatch,
using a code hash as an applicability proof, and calling matching fixture
outputs a general compiler. Preserve those distinctions in types and results.
No source-to-latent reconstruction or new accounting judgment is authorized by
the predicate evaluator. Existing portable definitions govern the scope.

## Evidence contract and sequence

1. Inspect existing truth machinery and selected actual method conditions.
   Record reused components and limitations before implementation.
2. Define a small closed predicate language, typed input declarations, stable
   requirement identities, separate false/unknown consequences, and immutable
   caller-selected manifest identity. Support explicit missing values without
   treating absence as zero, False, or an authoritative admission.
3. Implement structural/type validation separately from evaluation. Preserve
   all per-requirement findings and dependency references; distinguish known
   invalid input, unsupported scope, unavailable capabilities and unresolved
   findings. Assessment must not execute a method or certify accounting.
4. Compare selected manifest predicates with inspected native and retained
   conditions using changed known values, missing values, false/unknown caller
   findings and unavailable capabilities. Keep unexpressed prerequisites
   explicit. Add independent adversarial and truth-table cases, including
   repeated dependencies, cross-context comparisons and changed definitions.
5. Record deterministic checks, input locks, result and reproducible manifest;
   replay, refresh master controls and audit the next ready repair.

Pass requires correct typed semantics against independent expected cases,
matching selected original conditions, no mutation of retained packages, and
transparent residual conditions. Integrity failures, unsupported syntax accepted
as true, lost dependencies, authority escalation or false full-applicability
claims veto acceptance. They trigger repair; they do not reject simulator
research. Stop dependent work for corrupted evidence or an unresolved scientific
definition, while continuing independent internal work.

Truth-table totals and check counts are explanatory. They do not establish full
method coverage, accounting compliance, source admission, actual-company
feasibility, a complete compiler or production readiness. No stochastic ranking
is attempted. Historical fixtures remain synthetic or source-bound as labeled.
