# Establish shared-state compatibility before composing transitions

24 October 2026. S2-S4; MC05/06/11/13/16/17/20/24/26/28;
G2/G4/G13; interactions I01/I03/I04. Simulator-first execution continues.

## Question and skeptical audit

Can existing return and lease transition methods share one company state
without changing owner, source scope, currency, period, account meaning or
memory? The comparator is the original frozen state validators, transitions
and exact before/after fixtures, not the common invocation wrapper.

Inspection already shows different owners, dates and closed schemas. A positive
cross-module result based on renamed owners, a union of account keys or a
wrapper success would be wrong. First construct an executable compatibility
assessment that explains every relevant incompatibility and preserves unknown
semantics. Then use those findings to specify the smallest explicit shared-book
adapter and a new synthetic case. Never admit actual Henkel states or alter
the frozen native profiles. Do not spend another phase proving invocation.

## Evidence contract and intent ledger

Primary criterion: reproduce both native positive proposals; inspect and pin
their state schemas, account/flow/memory changes and scope policies; reject
unmodified cross-module sharing with explicit reasons; distinguish context
conflicts from missing semantic mappings. A compatible same-profile control
must retain before-state identity, exact rational effects and untouched memory.

Changed original results, an unaccounted state write, silently dropped
liability/equity/memory, or treating missing fields as zero veto the proposed
adapter. Unknown source or account equivalence vetoes admission, not further
design work. A finite control is explanatory evidence for a bounded profile,
not general composition, serializability, accounting compliance or durability.
Malformed/protected-source corruption is a continuation veto until repaired.

## Implementation sequence and assumptions

1. Protect exact native code, fixtures and invocation evidence. Record native
   validators, contexts, time bounds, account sets and all changed state paths.
2. Implement a read-only compatibility report with three-valued outcomes:
   incompatible for known contradictions, unresolved for absent semantic
   evidence, compatible only for the explicit same-profile/same-state control.
   A status must not authorize execution or turn on admission flags.
3. Check return/lease in both directions, shared-name accounts with different
   meaning, unknown context, changed source scope, stale state, and a real
   positive control. Save complete inputs, reports and direct native comparators.
4. Write the concrete next adapter design from those results: declared shared
   context, account maps, module-owned memory, read/write sets, immutable
   before-state binding, ordered pure application and conservation checks.
   If existing implementations cannot supply these safely, identify the exact
   successor changes; do not reinterpret failure as mission completion.

Original native calls are the reviewed baseline. A finite explicit registry is
an engineering choice; early rejection of invented profiles tests its limit.
Same account spelling is not equivalence. Unknown fields retain unknowns.
All examples remain synthetic and no reported issuer state is admitted.
This is deterministic reference engineering, not a forecast or performance
experiment. Run focused Python unit tests and a saved-case verifier; no GPU,
external service, new dependency, paid review or professional approval needed.
